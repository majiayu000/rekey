# Rekey v2 P-01 Password Lifecycle

**Date:** 2026-09-02
**Status:** Accepted for implementation
**Depends on:** Credential Authority v2 Foundation, H-07 closeout
**Scope:** password replacement, recovery-assisted password replacement, and recovery-key rotation

## 1. Goal

P-01 lets an operator replace either human unlock factor without decrypting or
rewriting stored Credentials. Both operations rewrap the existing in-memory VRK,
atomically retire the old wrapper, and preserve the v2 rule that no Agent API can
read a Secret.

This specification adds no new vault format, migration, compatibility path,
remote recovery service, escrow, or automatic unlock mechanism.

## 2. User-visible commands

```text
rekey password change [--recovery] [--stdin-secrets]
rekey recovery rotate [--password-stdin]
```

`rekey password change` requires the Broker to be unlocked. By default line 1
or the first hidden prompt is the current password. `--recovery` changes that
step-up proof to the current recovery key. In `--stdin-secrets` mode line 2 is
the new password. Interactive mode asks for the new password twice and rejects a
mismatch before sending an Admin request.

`rekey recovery rotate` also requires the Broker to be unlocked, but accepts
only the current password as step-up proof. The new recovery key is generated by
the Authority and returned once in the successful response body. It never
appears in argv, environment variables, JSON metadata, logs, or audit rows.
`--password-stdin` reads the current password from one bounded stdin line.

Recovery rotation deliberately does not accept the old recovery key as its only
proof. If delivery of the newly generated key fails after commit, the unchanged
password remains a known recovery path and the operator can rotate again.

## 3. Password replacement

The Authority processes password replacement as one serialized command:

1. Require the Authority to be unlocked and verify the supplied password or
   recovery step-up proof against the current active wrapper.
2. Reject an empty or larger-than-64-KiB new password.
3. Generate a new WrapperId, 16-byte salt, and AEAD nonce.
4. Derive a new password KEK with the compiled RFC 9106 low-memory Argon2id
   profile and wrap the already-unlocked VRK. Persist those exact parameters in
   the new wrapper row.
5. In one SQLite transaction, disable and cryptographically erase the old
   active password wrapper, insert the new active wrapper, and insert one
   `vault.password_changed(success)` audit row.
6. Return success only after commit.

The old wrapper row remains as non-secret lifecycle metadata. In the same
transaction its salt, nonce, and wrapped-VRK bytes are overwritten with
fixed-length tombstone bytes before it is marked disabled. Rekey does not claim
forensic erasure from SSD wear leveling, filesystem snapshots, or backups made
before the replacement.

A recovery-assisted change follows the identical transaction. It changes only
the password wrapper; the recovery wrapper remains active. The VRK, Credential
ciphertexts, action versions, policies, and live capability sessions do not
change.

## 4. Recovery-key rotation

The Authority processes recovery rotation as one serialized command:

1. Require the Authority to be unlocked and verify the current password.
2. Generate 32 random recovery bytes, encode them as `RKREC1`, and derive a
   recovery KEK with a new 16-byte salt.
3. Generate a new WrapperId and wrap the existing VRK.
4. In one SQLite transaction, disable and cryptographically erase the old
   active recovery wrapper, insert the new active wrapper, and insert one
   `vault.recovery_rotated(success)` audit row.
5. Return the new encoded recovery key once, in the Admin response body, only
   after commit.

The Broker and CLI keep the response body in zeroizing storage. A response write
failure cannot roll back a committed rotation. The current password remains
valid, so the documented recovery is to run `rekey recovery rotate` again and
save the latest key.

## 5. Atomicity and failure semantics

Exactly one active password wrapper and one active recovery wrapper must exist
before and after every successful command. The replacement transaction updates
exactly one active row of the selected kind; zero or multiple matches are
`STORAGE_INTEGRITY_FAILED` and fault the unlocked Authority.

The following failures commit no wrapper change:

- invalid step-up proof;
- empty or oversized new password;
- entropy, KDF, or AEAD failure;
- wrapper insert/update failure;
- transaction commit failure;
- success-audit insert failure.

An invalid proof returns the existing uniform `INVALID_UNLOCK_CREDENTIAL`
without identifying which internal check failed. The Authority first commits a
uniform denied-attempt audit event; if that audit cannot commit, it returns
`AUDIT_COMMIT_FAILED` and faults under the existing fail-stop contract. A
success-audit or wrapper-transaction commit failure has the same fail-stop
result, while rolling back the replacement. Other pre-commit failures return
their stable existing error and leave the old active wrapper usable.

A process stop around the transaction may expose either the complete old state
or the complete new state after SQLite recovery, never a vault with no active
wrapper or two active wrappers of the selected kind.

The Authority does not emit a success event before the wrapper transaction and
does not add a second mutable journal or closed error-code registry.

## 6. IPC contract

Two Admin message types are added:

| Message | Locked allowed | Step-up | Additional secret | Response |
| --- | --- | --- | --- | --- |
| PasswordChange | no | password or recovery | new password | empty body + non-secret receipt metadata |
| RecoveryRotate | no | password only | none | new recovery key in body + non-secret receipt metadata |

PasswordChange uses the existing bounded `proof + secret` body encoding.
RecoveryRotate uses the existing bounded proof body encoding. Both use empty
request metadata. A RecoveryRotate frame selecting recovery proof is rejected as
`INVALID_INPUT`; it is not silently reinterpreted.

Admin mutation coordination and the 25-second deadline apply before Authority
queue admission. Once the Authority begins the transaction, the Broker waits
for its definitive result and does not cancel an in-progress wrapper mutation.

## 7. Backup, restore, and lost-factor policy

Backups are complete encrypted snapshots and retain the wrapper set that was
active when each backup was created:

- a post-password-change backup opens with the new password or unchanged
  recovery key, never the old password;
- a post-recovery-rotation backup opens with the unchanged password or new
  recovery key, never the old recovery key;
- a pre-rotation backup still requires the factors belonging to that historical
  snapshot;
- restoring a backup never merges or reconciles wrappers with a newer vault.

Operational outcomes are explicit:

| Known material | Supported recovery |
| --- | --- |
| Password lost, recovery key known | Unlock with recovery, change password with `--recovery`, then optionally rotate recovery using the new password |
| Recovery key lost, password known | Rotate recovery and save the newly displayed key |
| New recovery response lost, password known | Rotate recovery again; only the latest displayed key remains active |
| Password and current recovery key both lost | Permanently unrecoverable; Rekey has no backdoor, escrow, reset, or Secret export |

Historical backups and external filesystem snapshots may remain unlockable by
their historical factors. Factor rotation is not retroactive destruction of
backup media.

## 8. Audit and secret handling

Successful commits add exactly one event of the corresponding type:

- `vault.password_changed`, outcome `success`, reason `password-step-up` or
  `recovery-step-up`;
- `vault.recovery_rotated`, outcome `success`, reason `password-step-up`.

Cryptographically invalid step-up proofs commit one uniform event before the
error response:

- `vault.password_change_failed`, outcome `denied`, reason `invalid-step-up`;
- `vault.recovery_rotation_failed`, outcome `denied`, reason `invalid-step-up`.

Rows contain no password, recovery key, KEK, VRK, salt, nonce, ciphertext, or
derived verifier. Existing `runtime.faulted` behavior remains authoritative when
an audited transaction cannot commit.

All request secret fields, generated recovery material, encoded recovery text,
KEKs, and temporary response buffers use existing zeroizing owners. The CLI
remains an IPC-only client and does not link Argon2, AEAD, SQLite, rekey-vault, or
rekey-broker.

## 9. Required verification

P-01 is complete only when all of the following are fresh and passing:

1. Authority contracts prove password-to-password and recovery-to-password
   replacement, old-password rejection, unchanged recovery access, one active
   wrapper per kind, and preserved Credential decryption.
2. Recovery contracts prove password-authorized rotation, old-key rejection,
   new-key unlock, response-loss retry, and preserved Credential decryption.
3. Transaction fault injection proves wrapper insert and audit/commit failures
   leave the prior wrapper active; success/denial audit failures also fault the
   worker.
4. Backup/restore contracts prove both post-rotation key sets and the explicit
   historical-backup behavior.
5. Real `rekeyd` + `rekey` black-box tests cover both commands, wrong proofs,
   stdin modes, old-factor rejection, and recovery-key body handling.
6. Canary scans prove passwords and both old/new recovery keys are absent from
   argv, environment, stderr/logs, audit metadata, and Rekey-created ordinary
   files; the new recovery key's intentional one-time stdout is the sole output
   exception.
7. Crash/reopen injection around the transaction observes either the complete
   old wrapper state or the complete new wrapper state, never a partial state.
8. `cargo check --workspace`, `cargo test --workspace`, `cargo fmt --all --check`,
   repository mechanical contracts, and exact-head CI pass.
9. README, user guide, operations runbook, Foundation boundary text, closeout
   plan, threat model, and Feature Truth Matrix describe the implemented limits
   without raising G1/G2 or release maturity.

## 10. Non-goals

- Changing or rotating the VRK or Credential DEKs.
- Password policy, breach lookup, password hints, escrow, or administrator
  bypass.
- Multiple simultaneous password or recovery wrappers.
- OS keychain, TPM, HSM, KMS, threshold recovery, or remote recovery service.
- Retroactively invalidating historical backups or storage snapshots.
- Changing capability/session, policy, connector, or Agent API semantics.
