# Rekey v2.0.0-alpha.2

Public Alpha of the Rekey v2 local Credential Authority on vault schema **v9**.
This file describes the `v2.0.0-alpha.2` archive (Shape A). The tagged workflow
publishes a prerelease before public-URL smoke. Treat that Release as the
completed public download only after smoke succeeds; a smoke failure withdraws
it to draft. Until then, `v2.0.0-alpha.1` remains the last completed public
download.

## Breaking: schema v9, new empty directory

This is not an in-place upgrade from `v2.0.0-alpha.1` (schema v5).

1. With the **old** binaries, create and verify a backup. Save the receipt and
   SHA-256 off the state directory.
2. Stop the old service. Keep the old state directory and matching old binaries.
3. Install this archive's `rekey` and `rekeyd`. Initialize a **new empty**
   directory. Recreate credentials, Actions, policy trust, signed policy, and
   any workload or Vault source profiles through supported Admin operations.
4. Unlock, mint a new session, and complete one authorized execute.

The old backup restores only with those old binaries into a newly created empty
directory. It is not an import into v9. v5 binaries cannot open v9 state, and
v9 binaries cannot open any other format, including v1 and v4–v8. Mismatched
directories are rejected and left untouched.

After public-URL smoke succeeds, `v2.0.0-alpha.1` remains a historical
v5 archive for that rollback path only. There is no reader, migration, or
dual-format support.

## Scope

Supported artifacts: macOS 14 Apple silicon arm64 and Ubuntu 24.04 x86_64.

| Capability | This archive | Limit that remains |
| --- | --- | --- |
| Local credentials, fixed HTTPS Action, backup/restore | included | G1, one local Authority |
| Password change, recovery rotation | included | no historical-backup invalidation; no VRK/DEK rotation |
| Audit list/export | included | no remote delivery, deletion, or configurable retention |
| Signed policy, one- and two-person approval | included | external signatures only; no approval service or private-key custody |
| Workload identity | included | static public keys; no JWKS/discovery |
| GitHub App closed profile (`github-app-installation-v2`) | included | one installation; 1–16 exact repositories; `GET /installation/repositories` and `POST /repos/OWNER/REPOSITORY/issues` only; live `api.github.com` evidence does not cover every added Admin path |
| Vault KV v2 and one-shot dynamic lease | included (Shape A) | fixture-only closed protocol; no private-network source; no live Vault OSS interoperability |
| Linux `agent-run` | included | bubblewrap; disjoint socket; Ubuntu AppArmor profile; Black-box Verified facts only |

The IO-free `rekey-connector` crate is in the git tree at this tag, not in the
downloadable archive. It is not an MCP server or generic OAuth connector.

Out of this Alpha: Shape B Vault cut, other cloud secret sources, MCP server,
online JWKS, P-08 metrics, P-10 plugin isolation, macOS sandbox, general G2, and
an enterprise control plane.

## Security boundary

The default deployment is G1: one trusted local user administering agents under
that same user. The Linux container/namespace G2 reference is separate,
bounded evidence and is not the default deployment. Linux `agent-run` does not
change that default, does not replace the Docker G2 harness, and is not
Adversarially Verified isolation. Rekey does not protect against host root,
kernel compromise, same-user process inspection, or direct agent egress outside
those documented topologies.

## Known limitations

- No v1 migration, Windows build, macOS G2 claim, arbitrary URL proxy,
  redirects, SSE, Agent-visible streaming, dashboard, control plane, or HA.
- Response sealing detects raw, base64, base64url, percent-encoded and
  chunk-boundary reflections; it cannot detect every compressed, encrypted,
  derived, or application-specific encoding.
- Password attempt throttling and in-memory capability/approval-use state
  reset when the broker process restarts. Complete valid database snapshot replay
  is not detected.
- Vault sources in this archive are fixture-bounded. Registering a profile is
  not live HashiCorp Vault interoperability. A hard crash may leave a dynamic
  lease active until Vault expires it.
- Factor replacement is not retroactive. A backup still requires the password
  or recovery key that was active when it was created.

## Install and verify

Follow `docs/installation.md`. After the GitHub Release exists, verify
`SHA256SUMS` and the GitHub artifact attestation before extracting an archive.
Both binaries must print `2.0.0-alpha.2`. `rekey status` on an initialized
broker reports `"format_version": 9`.

## Upgrade and rollback

Follow the cross-version path in `docs/installation.md`. Roll back by restoring
the matching pre-cut backup with the preserved **old** binaries into a new
empty directory. Never point those binaries at a directory a v9 process has
opened, and never point a v9 binary at older state.
